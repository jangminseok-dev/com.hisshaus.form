# 히스하우스 예약 신청서 웹 — 설계

작성 2026-10-23. 사용자(장민석)와 브레인스토밍으로 정한 것을 담는다. 이 문서만 읽고 계획을 세울 수 있어야 한다. 문항 원문은 같은 폴더의 `2026-10-23-hisshaus-form-questions.md` 에 있다.

## 1. 무엇을 왜 만드나

반려동물 미용 매장 **히스하우스(Hiss Haus)** 는 지금 예약 신청을 구글폼 두 개로 받는다.

- **예약 신청서**(14문항): 예약하려는 보호자 모두가 쓴다.
- **심층 행동 분석 검사지**(98문항): 교육미용(미용 트레이닝) 상담을 원하는 보호자만 쓴다. 지금은 사장님이 상담 뒤에 링크를 따로 보낸다.

실제 운영 흐름(사장님 김재성 님 말):

> 예약한다고 하면 신청서 작성해 달라고 하고 → 보호자가 원하는 날짜·시간대에 가능하면 예약해 주고 → 안 되면 조율해서 확정 → 예약금 만 원 입금되면 확정.

이걸 **히스하우스 전용 웹페이지**로 옮긴다. 목표는 둘이다.

1. 보호자가 폰에서 **편하게** 쓴다. 참고한 모양은 케끄(caeque.com)의 주문서 — 첫 화면에 매장 사진·소개·큰 버튼, 그 뒤는 한 화면에 한 주제씩 넘기고, 아래에 고정 버튼이 있는 구조.
2. 제출되면 **사장님이 슬랙으로 바로 안다**. 메시지 안에 답변 전체가 들어 있고, 기록은 따로도 쌓인다.

이건 차곡노트 플랫폼 기능이 아니라 **히스하우스 하나를 위해 먼저 만들어 보는 것**이다. 차곡노트 백엔드·앱과 연결하지 않는다. 나중에 플랫폼으로 올릴 때 화면과 문항 정의를 가져갈 수 있으면 좋지만, 그걸 위해 지금 추상화하지는 않는다.

## 2. 목표 · 비목표 · 반목표

**목표**
- 구글폼보다 쓰기 편하다. 특히 폰에서.
- 신청서가 제출되는 순간 슬랙에 답변 전체가 간다.
- 답변이 구글 시트에 한 줄씩 쌓여 사장님이 지금 보던 대로 본다.
- 교육미용을 고르면 검사지로 바로 이어진다. 잘못 골랐으면 빠져나올 수 있다.
- 검사지 98문항은 중간에 닫아도 쓰던 자리로 돌아온다.

**비목표**(이번에 안 한다)
- 결제·예약금 입금 확인·예약 확정 관리. 입금 확인은 사장님이 지금처럼 수동으로 한다.
- 사장님용 관리 화면. 기록은 구글 시트가 전부다.
- 로그인·회원. 보호자는 로그인 없이 쓴다.
- 보호자에게 가는 알림(카카오 알림톡·문자). 사장님이 직접 연락한다.
- 차곡노트 백엔드·앱·알림장 웹과의 연동.
- 예약 가능 시간표·캘린더 연동. 희망 일시는 "희망"일 뿐이다.
- 검사지 문장 다듬기. **검사지 98문항은 오타까지 원본 그대로** 쓴다(사용자 결정 2026-10-23).

**반목표**(이렇게 되면 되어도 실패)
- 구글폼보다 번거롭다(화면이 더 많아졌는데 할 일이 늘어남, 입력이 날아감).
- 보호자가 쓴 개인정보가 사장님 슬랙·시트 말고 다른 곳으로 간다(로그, 외부 분석 도구, 브라우저에서 제3자 호출).
- 교육미용 손님이 검사지 도중에 나갔는데 사장님이 신청 자체를 모른다.
- 웹훅 주소·서비스 계정 키 같은 비밀값이 코드·로그·커밋에 남는다.

## 4. 화면 흐름

브라우저 목업으로 보여 주고 사용자가 확인한 흐름이다. 전부 폰 세로 화면 기준으로 그리고, 데스크톱은 가운데 폭 제한(약 480px)으로 같은 화면을 보여 준다.

### 4.1 예약 신청서

```
[0 첫 화면] ─ 예약 신청하기 ─▶ [1 보호자] ─ 다음 ─▶ [2 반려견] ─ 다음 ─▶ [3 희망 일시·서비스] ─ 신청하기 ─▶ (제출)
                                                                                                  │
                                            교육미용 안 고름 ◀──────────────────────────────────┴──────▶ 교육미용 고름
                                                 │                                                           │
                                            [5 완료]                                                [4 검사지 안내]
                                                                                                  시작 ─▶ 검사지 흐름(4.2)
                                                                                                  "교육미용은 아니에요" ─▶ [5 완료]
```

**[0 첫 화면]**
- 위: 매장 이름 "Hiss Haus"(작은 로고 자리).
- 큰 사진 한 장(사장님이 고른 매장 사진. 자리만 만들고 실제 파일은 사용자가 넣는다).
- 제목 "예약 신청서".
- 안내문(해요체로 옮김): "이 신청서는 예약 확정이 아니에요. 신청서를 확인한 뒤 따로 연락드리고, 최종 안내를 받으면 예약이 확정돼요." 구글폼 원문의 "아이의 편안한 케어를 위해 충분한 상담 후 예약을 진행합니다"도 해요체로 넣는다.
- 정보 줄: 위치 / 영업시간 / 예약금("10,000원 입금 시 확정"). 소요 시간 줄은 **없다**.
- 아래 고정 버튼 "예약 신청하기".

**[1 보호자]** 보호자 성함, 보호자 연락처, 개인정보 수집·이용 동의(아래 6.4).

**[2 반려견]** 이름, 견종, 나이, 몸무게, 성별(남/여), 중성화(O/X), 예방접종(O/X), 건강 상태(장문), 최근 수술·치료 이력(장문), 공격성(O/X, O 옆에 원문 안내 "심한 경우 이용에 제한이 될 수 있는 점 양해부탁드립니다"를 해요체로).

**[3 희망 일시·서비스]**
- 희망 날짜 1순위(필수): 날짜 선택 + 시간대 칩(오전 / 오후 / 상관없어요).
- 희망 날짜 2순위(선택): 같은 모양.
- 이용 서비스(복수 선택, 필수): Grooming 미용 / Daycare 데이케어 / Hotel 호텔 / 교육미용·미용 트레이닝 상담.
- 방문(필수): 첫 방문 / 재방문.
- 안내 한 줄: "원하는 날짜와 시간대를 알려 주시면 가능한지 확인하고 연락드려요. 안 맞으면 함께 조율해요."
- 버튼 "신청하기" → 여기서 **제출**된다.

**[4 검사지 안내]** (교육미용을 골랐을 때만, 제출 성공 뒤)
- "심층 행동 분석 검사지를 이어서 작성해요"
- "중간에 창을 닫아도 쓰던 자리가 저장돼요."
- 상자: "예약 신청은 여기서 먼저 접수돼요. 검사지를 다 못 써도 신청은 히스하우스에 전달돼요. 검사지는 나중에 같은 링크로 이어서 쓸 수 있어요."
- 버튼 "검사지 작성 시작" / 보조 버튼 "교육미용은 아니에요".
- "교육미용은 아니에요"를 누르면: 슬랙에 짧은 취소 알림을 보내고(6.2) [5 완료]로 간다. 시트 행은 고치지 않는다(내 결정 — 시트 수정은 복잡도만 늘고 슬랙 알림으로 충분).
- 문항 수·소요 시간은 **적지 않는다**.

**[5 완료]**
- "신청이 접수되었어요"
- 요약 한 줄: "{반려견 이름} · {서비스} · {1순위 날짜} {시간대} 희망"
- 다음 순서 상자: "1. 히스하우스가 신청서를 확인하고 연락드려요 / 2. 날짜·시간을 맞춘 뒤 예약금 10,000원을 입금해 주세요 / 3. 입금이 확인되면 예약이 확정돼요"
- "{연락처 가운데 가림} 로 연락드려요."
- 교육미용을 골랐고 검사지를 아직 안 썼으면 "검사지 이어서 쓰기" 링크를 하나 둔다(내 결정).

### 4.2 검사지(교육미용)

- 진입: [4 검사지 안내]의 "검사지 작성 시작", 또는 `/survey` 주소를 직접 열었을 때.
- 구글폼의 섹션을 그대로 묶음(단계)으로 쓴다. 섹션 제목이 없는 식사 구간(Q33~44)은 "식사·간식" 같은 이름을 빌더가 붙인다. 묶음 수는 11~12개.
- 각 묶음 위에 진행 표시(점 또는 막대). 숫자로 "n/12"는 보여 줘도 되지만 "98문항"처럼 **전체 문항 수는 적지 않는다**.
- 첫 묶음의 의뢰인 성함·연락처는 신청서에서 쓴 값을 미리 채운다(브라우저에 남아 있을 때).
- 마지막 묶음의 버튼 "제출하기" → 제출 → "검사지가 접수되었어요" 완료 화면.
- 검사지를 다 쓰기 전에 나갔다가 다시 `/survey`를 열면 마지막으로 쓰던 묶음으로 돌아온다.
- 신청서 없이 `/survey`를 바로 열어도 쓸 수 있다(사장님이 기존 방식대로 링크만 보낼 수 있게). 이때 신청 ID는 없다.

### 4.3 공통 동작

- 위 뒤로 가기(‹)는 이전 묶음으로. 브라우저 뒤로 가기도 같은 뜻으로 동작한다(묶음마다 history 한 칸).
- 아래 고정 버튼은 그 묶음의 필수 항목이 다 채워질 때까지 비활성(회색). 비활성 상태에서 누르면 비어 있는 첫 항목으로 스크롤하고 빨간 안내를 보여 준다.
- 입력은 **묶음을 넘길 때와 입력할 때마다** 브라우저(localStorage)에 저장한다. 같은 기기·같은 브라우저에서만 복원된다. 다른 기기에서는 처음부터다. 이건 보호자에게 설명하지 않는다(기대를 만들지 않는다).
- 제출 성공 뒤 신청서 초안은 지운다. 검사지 초안은 검사지 제출 성공 뒤 지운다. 신청 ID·교육미용 선택 여부·보호자 이름·연락처·반려견 이름은 완료 화면·검사지 미리 채우기·"이어서 쓰기"를 위해 세션으로 남겨 두고, 새 신청을 시작할 때 지운다.
- 제출 중에는 버튼이 "보내는 중…"으로 바뀌고 두 번 눌리지 않는다.
- 제출 실패(서버 오류·네트워크): "지금은 보낼 수 없어요. 잠시 뒤 다시 눌러 주세요." 입력은 그대로 남아 있다.

## 5. 문항

전체 문항·선택지·필수 여부는 `2026-10-23-hisshaus-form-questions.md` 에 있다. 요약:

- 신청서: 구글폼 14문항 + 희망 날짜 1순위(필수) + 2순위(선택) + 개인정보 동의(필수).
- 검사지: 구글폼 98문항 **원문 그대로**. 필수 표시도 원문대로.
- 검사지의 "기타: (직접 입력)" 선택지는 고르면 바로 아래 한 줄 입력이 열린다.
- 검사지 문항 유형 중 "단답/장문 구분 불가"로 적힌 것은 빌더가 질문 길이로 정한다(짧은 답이 예상되면 한 줄, 아니면 여러 줄). 틀려도 데이터는 같다.
- **원문 그대로의 범위는 글자다.** 질문·선택지·안내문은 한 글자도 바꾸지 않는다. 다만 원문이 글로만 안내하던 흐름을 화면 동작으로 옮길 때 생기는 모순은 고친다(내 결정, 검토에서 나옴). 둘뿐이다:
  - 검사지 Q83(공격행동 상황)에서 "없음"만 골랐으면 Q84·Q85는 필수를 풀고 건너뛴다(원문 안내 "없음 체크하시고 아래 문항 건너뛰셔도 됩니다"를 그대로 동작으로 옮긴 것). Q86~95는 원래 선택이다. 슬랙·시트에는 빈 값으로 간다.
  - 검사지 Q2(의뢰인 동의)에서 "동의하지 않음"을 고르면 그 자리에 "동의하지 않으면 검사지를 진행할 수 없어요"를 보여 주고 다음 버튼을 막는다. 서버도 이 값이면 거부한다(개인정보를 동의 없이 받지 않는다). 원문은 분기 없이 제출되지만 그대로 옮기면 동의 없는 개인정보를 받게 되므로 고친다.
  - 조건부 문항(Q50·Q60·Q62·Q82)은 앞 문항이 "네/예"일 때만 보인다. 아니면 숨기고 빈 값.

## 6. 어떻게 만드나

### 6.1 스택(내 결정)

- **Next.js(App Router) + TypeScript + pnpm**. 차곡노트의 알림장 웹과 같은 스택이라 사용자가 익숙하다. 버전은 빌더가 만드는 시점의 안정판.
- 글꼴은 Pretendard를 `next/font/local` 로 싣는다(외부 글꼴 호출 없음). 차곡노트 웹과 같은 방식.
- 외부 스크립트·분석 도구·외부 CDN을 넣지 않는다. 브라우저가 부르는 곳은 이 웹 자신뿐이다.
- 스타일 도구(CSS Modules / Tailwind 등)는 빌더가 정한다. 다만 색·간격은 한 곳에 토큰으로 둔다.
- 문항은 **TypeScript 데이터**로 정의한다(질문 문구·유형·선택지·필수·묶음). 화면은 그 데이터를 읽어 그린다. 신청서와 검사지가 같은 렌더러를 쓴다. 슬랙 메시지와 시트 행도 같은 정의에서 만든다 — 문항이 바뀌면 한 곳만 고친다.

### 6.2 제출 처리(서버)

브라우저는 이 웹의 서버(Route Handler 또는 Server Action)에만 보낸다. 서버가 구글 시트와 슬랙을 부른다. 비밀값은 서버에만 있다.

**신청 ID**는 **브라우저가** 첫 제출을 누를 때 만들어 초안과 함께 보관한다(무작위 10자, 영숫자). 재시도해도 같은 ID로 보낸다. 서버는 형식만 검증한다. 검사지 제출도 같은 ID를 실어 보낸다(있을 때). 그래서 시트에 같은 ID가 두 줄이면 같은 제출의 재시도다.

**순서**: ① 입력 검증(형식·필수·길이·허니팟·신청 ID 형식) → ② 구글 시트에 한 줄 추가 → ③ 슬랙 전송 → ④ 브라우저에 성공 응답.

- ② 실패 → 400/500 으로 실패를 알리고 브라우저는 재시도 안내. 슬랙은 보내지 않는다.
- ③ 실패 → **성공으로 처리**한다(기록은 남았다). 서버 로그에 "슬랙 전송 실패 + 신청 ID"만 남긴다(답변 내용은 로그에 안 남긴다). 사장님은 시트에서 본다.
- 응답은 슬랙까지 끝난 뒤 준다(내 결정). 그래서 슬랙 메시지 수를 줄인다(아래). 서버 함수 시간 제한은 30초로 올린다(`maxDuration`, Next 표준 설정). 응답을 먼저 주고 슬랙을 뒤에서 보내는 방식(Next `after()`)은 써도 되지만 필수는 아니다 — 쓴다면 "슬랙 실패 시 성공 응답" 규칙은 자연히 성립한다.
- 재시도로 같은 ID의 행이 두 줄 생길 수 있다. 서버에서 막지 않는다(내 결정 — 중복 제거는 사장님이 시트에서 ID로 한다).

**슬랙**: Incoming Webhook 하나. Block Kit으로 보낸다.
- 신청서: 메시지 한 통. 머리글 "🐾 새 예약 신청 — {반려견 이름} ({보호자 성함})", 그 아래 모든 문항을 "질문: 답" 줄로. 마지막에 신청 ID와 접수 시각.
- 검사지: 답변이 길다. 한 통에 **최대한 채워** 보낸다 — 섹션 블록 하나에 3,000자까지, 메시지 하나에 블록 50개까지, 메시지 전체는 약 30KB를 넘기지 않는다. 묶음 경계가 아니라 **한도에 닿을 때** 자른다. 보통 1~3통이면 된다. 첫 통 머리글 "📋 행동 분석 검사지 — {반려견 이름} ({의뢰인 성함})", 둘 이상이면 "(k/N)"을 붙인다. 신청 ID가 있으면 첫 통에 "예약 신청 {ID}의 검사지"라고 적는다. 웹훅은 초당 1건이므로 순서대로, 사이에 1초 쉬어 보낸다.
- 취소: "교육미용은 아니에요"를 누르면 "↩️ {반려견 이름} ({보호자 성함}) 보호자가 교육미용 선택을 취소했어요 (신청 {ID})" 한 통.
- 답변 글자는 슬랙 mrkdwn 특수문자(`<`, `>`, `&`)를 이스케이프한다.

**구글 시트**: 스프레드시트 하나에 탭 둘 — "예약신청", "검사지". 서비스 계정으로 `append`. 열 순서는 문항 정의 순서이고, 맨 앞에 접수 시각(KST)·신청 ID. 복수 선택은 ", " 로 잇는다. 첫 줄(헤더)은 빌더가 스크립트 또는 문서로 제공하고, 사용자가 시트를 만들 때 붙인다. 시트를 서비스 계정 이메일에 편집자로 공유해야 한다(설정 문서에 적는다).

### 6.3 설정·비밀값

- 환경변수 셋: `SLACK_WEBHOOK_URL`, `GOOGLE_SERVICE_ACCOUNT_JSON`(base64 한 줄), `GOOGLE_SHEET_ID`. 로컬은 `.env.local`(git 제외), 운영은 Vercel 환경변수.
- `process.env` 는 설정 모듈 한 곳에서만 읽는다. `NEXT_PUBLIC_` 변수를 만들지 않는다(브라우저로 나갈 값이 없다).
- 셋 중 하나라도 없으면 서버가 뜰 때 변수 **이름**만 담아 오류를 낸다.
- 웹훅 주소·키·답변 내용·요청 본문을 `console.*` 에 넣지 않는다.
- 매장 정보(이름·주소·영업시간·예약금 문구·사진 파일명·계좌 안내 유무)는 코드 안의 내용 파일 한 곳에 둔다. 비밀이 아니므로 커밋한다. 실제 값은 사용자가 채운다(지금은 자리 표시).

### 6.4 개인정보

- 신청서 [1 보호자] 묶음에 "개인정보 수집·이용 동의" 필수 체크를 둔다(내 결정 — 개인정보보호법상 필요). 내용: 수집 항목(보호자 성함·연락처, 반려견 정보), 목적(예약 상담·안내), 보유 기간(예약 종료 후 N년 — N과 정확한 문구는 사용자/사장님이 정한다. 자리 표시로 "1년").
- 검사지는 원문의 "의뢰인 동의" 문항을 그대로 둔다.
- 응답 헤더에 `X-Robots-Tag: noindex` 는 **달지 않는다**(사장님이 링크를 퍼뜨리는 공개 페이지다). 대신 완료 화면·검사지 화면처럼 개인정보가 보이는 화면은 `Cache-Control: private, no-store`.
- 카카오톡 미리보기용 OG 태그(제목 "히스하우스 예약 신청", 설명 한 줄, 매장 사진)를 첫 화면에 넣는다.

### 6.5 스팸·오남용

- 폼에 숨은 허니팟 칸 하나. 값이 있으면 조용히 200 을 주고 버린다.
- 서버 측 글자 수 상한(짧은 답 200자, 긴 답 3,000자)과 필수·선택지 검증. 브라우저 검증을 믿지 않는다.
- 요청 빈도 제한은 넣지 않는다(서버리스라 메모리 제한이 의미 없고, 유료 저장소를 붙일 만큼의 위험이 아니다. 내 결정).

### 6.6 테스트·검증

- 단위(Vitest): 문항 정의 → 시트 행 변환, 문항 정의 → 슬랙 블록 변환(글자 한도·분할·이스케이프), 입력 검증(필수·선택지·길이·허니팟), 초안 저장·복원.
- 서버: 가짜 슬랙·가짜 시트를 두고 제출 순서(시트 실패 시 슬랙 안 감, 슬랙 실패 시 성공 응답)를 본다.
- 브라우저(Playwright): 신청서 끝까지 → 완료, 교육미용 → 검사지 안내 → 취소, 교육미용 → 검사지 몇 묶음 쓰고 닫았다 열어 복원, 폭 320·390 에서 가로 넘침 없음, 뒤로 가기.
- 테스트 이름·주석은 한국어.

### 6.7 배포

- Vercel, 사용자 계정, 무료(Hobby) 플랜. **위험**: Hobby 약관은 비상업용이다. 매장 예약 접수는 상업용으로 볼 여지가 있다. 사용자가 알고 무료로 간다고 정했다(2026-10-23). 문제가 생기면 Pro(월 20달러) 또는 Cloudflare Pages로 옮긴다. 코드가 Vercel 전용 기능에 기대지 않게 한다.
- 도메인 `hisshaus.chagocnote.com` 은 나중에 붙인다. 그때까지는 Vercel 기본 주소.
- CI 는 처음엔 두지 않는다. 로컬에서 테스트·빌드를 돌리고 푸시한다. GitHub 저장소 생성은 사용자가 한다.

## 7. 빌더에게 맡기는 것

- 폴더 구조, 상태 관리 방식, 스타일 도구.
- 날짜 선택 UI(달력 vs 네이티브 date input). 오늘 이전은 못 고른다.
- 진행 표시 모양, 칩/라디오/체크박스 디자인. 톤은 케끄처럼 흰 배경·큰 사진·포인트 색 하나. 포인트 색은 히스하우스 사진에 어울리는 중성색으로 빌더가 고르고 토큰 한 곳에 둔다.
- 검사지의 긴 선택지 목록(Q69 23개, Q83 48개) 표시 방식.
- 슬랙 블록의 정확한 구성(필드 블록 vs 섹션 블록)과 분할 경계.
- 시트 헤더를 만드는 방법(스크립트 vs 문서 안내).
- 설정·운영 문서(README): 슬랙 웹훅 만들기, 서비스 계정 만들기·시트 공유, Vercel 환경변수, 매장 사진 넣기.

## 8. 성공 기준

- 폰에서 신청서를 처음부터 끝까지 쓰고 제출하면 몇 초 안에 슬랙에 답변 전체가 오고 시트에 한 줄이 생긴다.
- 교육미용을 고르면 검사지로 이어지고, "교육미용은 아니에요"로 빠지면 취소 알림이 온다.
- 검사지를 쓰다 닫았다 열면 쓰던 묶음으로 돌아온다.
- 화면 어디에도 "~입니다" 체, 문항 수, 소요 시간이 없다.
- 비밀값이 git 이력·빌드 산출물·로그에 없다.
